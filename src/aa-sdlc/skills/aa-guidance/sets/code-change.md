# Guidance set `code-change`

What every step that changes code, configuration, or infrastructure does, on top of repository-write: format changed files, prove with the build and tests, plan before a multi-step change, reference the ticket, commit everything needed to build and operate, let the tools decide style, change dependencies through the package manager, and never let a hand-edited feature file through.

Generated from `src/aa-sdlc/workflow/guidance-sets/code-change.yaml` and `docs/guidance.md` by `scripts/Sync-SkillGuidance.ps1`; do not edit by hand.

- **G-01** Always format the code for the changed files before committing, but do not format files that were not changed.
- **G-04** During development run focused checks; before review run the affected build, lint and relevant test tiers, retaining actual output and declaring the scope. At actual branch finish run full build, lint, provenance and every test tier; at release satisfy the release checks. Instruction-only changes use the framework's applicable structural validation rather than claiming product behavior.
- **G-08** Confirm one proportionate brief before a multi-step change: scenarios, boundaries, invariants, owned paths, proof and next runnable join. Approval covers implementation through review within that boundary; honor delegated approval authority, record routine adjustments and renew approval for material requirement, scope, public contract, schema/wire, dependency or authority changes.
- **G-09** Reference the anchor ticket in the branch name and every commit message.
- **G-11** Every artifact that belongs with the code goes into the same task-owned change set as the code, staged or committed under G-40. Nothing that matters is left only in a conversation or unrecorded on a local disk.
- **G-33** Write every commit message in Conventional Commits form: a type from the project's list, an optional scope, an imperative subject, a body that says why, and a footer carrying the ticket reference and any breaking change. One concern per commit (G-39); if you cannot name the type, split the commit.
- **G-37** Commit everything needed to build, deploy, and operate the software with the change that needs it: configuration templates, migrations, scripts, pipeline, infrastructure, container, and alert definitions, runbooks, and the development environment configuration. If a fresh clone plus the documented secrets could not build, deploy, and run the system after your change, something is missing from the repository; find it and commit it.
- **G-39** Make each commit one understandable change: one concern per commit, one ticket per branch, a subject that says what and a body that says why, small enough to review in one sitting. If the subject needs "and" or the diff needs a tour, split it.
- **G-40** Commit only with explicit user authorization, including standing permission for local commits within a named task until revoked or its scope ends. Without it, stage only task-owned changes and present the diff and message; do not stop for authorization already granted. Implementation alone does not authorize commits, and local commit permission grants no delegation, remote-write, protected-merge or release authority; use the user's identity without agent attribution.
- **G-42** Before making a change, name what it is for: the ticket, the scenario it satisfies, or the decision record or page that explains it, and put that reference where the change lives: the branch, the commit footer, the merge request, and the artifact. A change that cannot name its purpose is a ticket to create first or work not to do; in review, a hunk that traces to nothing is a finding.
- **G-44** Let the tools decide style: conventions live in the repository as formatter configuration and a static analyser rule set, the formatter runs on changed files and the analyser runs from the root build before a change is presented, and every finding is fixed or suppressed with a reason beside it. Never argue style in review; where a language has no known linter, record that once in the development environment configuration and expect the health warning.
- **G-45** Change dependencies only through the ecosystem's package manager: add, update, and remove with its commands so it resolves conflicts, surfaces warnings, and updates transitive dependencies and the lock file together, and stage the manifest and lock file changes as their own commit (G-39). Never edit a version in a manifest or lock file by hand; if the tool refuses, record the refusal on the ticket and resolve it, never bypass it.
- **G-56** Before a change is committed and before it is merged, check the feature files: every one carries its provenance header, matches its checksum, and is generated by a page. Refuse a change that fails, and say to change the page and pull it instead.
- **G-59** Keep one proportionate evidence index on the ticket or its linked durable record: candidate and dependency identity, executor and independence, requirement/environment identity, commands and actual results, required coverage, findings and owned-resource cleanup. One independently executed combined-candidate gate may serve reviewer and integrator for its named scope; reference unchanged proof, rerun affected proof when relevant inputs or evidence validity changes, and never relabel scoped integration as full branch finish or release.
- **G-60** Establish meaningful failing behavior, then evolve tests and code together; after the first focused behavior exercise the brief's real collaborator before broad private/unit matrix expansion. Preserve independent public/persisted-contract evidence and applicable authority, money, malformed-data, clock, race, lifetime and cleanup checks; when a collaborator is unavailable, record the missing join and continue independent work without claiming integration.
- **G-61** Name the actual constrained resource, its owner and release condition, checking observed capacity before extending waits to independent work. Preflight expensive runs against actual transition/accounting state, tested dependency identity and usable artifact paths; existing scoped ownership covers routine changed-cause setup repairs without another start approval, with handle, terminal-result and cleanup reporting, while ownership or material scope changes require coordination.
